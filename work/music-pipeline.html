The music pipeline

A one-way sync that takes a self-hosted music library and prepares it for an old MP3 player — without me thinking about it.

Role
Owner & operator
Timeline
2025
Stack
Python, rclone, ffmpeg, FAT32
Output
Incremental, verified MP3 library

The problem

The music library lives on a self-hosted Seafile instance. The player is an old Bluetooth MP3 player with opinions: it only understands FAT32, chokes on long or non-ASCII filenames, and sorts by filename rather than tags. Copying files by hand worked once, then became a small chore every time the library changed.

I wanted a repeatable one-way pipeline: source library in, player-ready SD card out, with no chance of writing back to the library.

The pipeline

  1. Read-only source. The library is mounted through rclone in read-only mode. The sync can read music; it cannot modify or delete the source.
  2. Scan and compare. The script walks the library and compares each track against what is already on the card. Existing files are skipped, so a re-run is cheap.
  3. Transcode when needed. MP3 sources are copied bit-for-bit. FLAC sources are encoded to 320 kbps CBR MP3.
  4. Make the names boring. Artist, album, and track names are transliterated to ASCII and stripped of FAT32-illegal characters, then written in a predictable Artist/Album/NN - Title.mp3 layout.
  5. Tag for old firmware. Every output gets both ID3v2.3 and ID3v1 tags, because the player’s idea of “modern” stopped somewhere around 2004.
  6. Verify the result. Each written file’s duration is checked against its source. A mismatch is reported instead of silently shipped.

Edge cases that mattered

  • FAT32 limits. Long paths and characters that are legal on Linux are not legal on the card. Sanitizing names is not cosmetic; it prevents files that the player cannot open.
  • A corrupt source file. One track in the library had no valid MPEG frames. The scanner logs it and skips it rather than failing the whole run.
  • Old firmware. The player caps usable SD capacity. The pipeline handles the card it is given; the fallback is a smaller card, not a different format.
  • Repeat runs. The sync is idempotent. Running it twice does not duplicate files or re-encode what is already correct.

Safety rails

The card-format helper is intentionally annoying. It refuses to run against an ambiguous disk, and it will not proceed until you type WIPE at the prompt. The sync itself defaults to a dry run when I am testing a new source path, and the source mount is read-only by design.

Those rails are not distrust of the script. They are recognition that a tired person at 11 p.m. is part of the system too.

What I’d improve

  • Move the device-specific rules into a small profile file so a second player does not mean a second script.
  • Add a manifest so the card can be verified later without rescanning the source.
  • Schedule it from systemd when a card is inserted, instead of running it manually.
  • Surface a one-line summary at the end: copied, skipped, transcoded, failed.

What I learned

Most of the work in this project was not audio. It was understanding the actual device: its filesystem, its filename limits, its firmware, and the way it sorts a list. Designing for the real target — not the ideal one — is the same instinct that makes infrastructure reliable.

It also reinforced a rule I keep coming back to: verify the output. A file that exists is not the same as a file that plays.
