The brief

I wanted three things from a home server: my files and photos on hardware I control, no services exposed directly to the internet, and a recovery plan that survives a dead disk. Everything else was negotiable.

The constraint that shaped the build was not storage or CPU. It was maintenance. A lab that needs attention every week is a hobby; a lab that quietly runs for months is infrastructure. I optimized for the second one.

The shape of it

One Linux host runs the services in Docker. The system disk is LUKS-encrypted, and the live data sits on that encrypted volume. Nextcloud handles files, calendars, and contacts; Seafile holds the music library; Immich handles photos. Tailscale is the only way in.

Backups run nightly with restic to a separate 1.8 TB USB drive. A second timer mirrors that repository to another machine off-site, and a weekly job reads back a random 5% sample to verify it. Nothing is reachable by a public IP, and no service assumes it is safe just because it is behind the VPN.

A note on detail: this write-up deliberately omits hostnames, addresses, ports, and credentials. The architecture and the trade-offs are the point.

What runs

  • Nextcloud — files, calendars, and contacts, synced to a phone and laptop over CalDAV and CardDAV.
  • Seafile — the music library, exposed read-only to the sync pipeline through an rclone mount.
  • Immich — the photo library and mobile backup target.
  • Docker — every service runs in a container, which keeps upgrades and rollbacks predictable.
  • Backups — nightly restic snapshots to a separate USB drive, an off-site mirror, and a weekly read-verification.
  • Updates — nightly OS, firmware, and container updates from a systemd timer.

Three problems worth writing down

1. Syncing contacts without creating duplicates

Google is still the source of truth for contacts, so I wrote a one-way sync from Google Contacts to Nextcloud’s CardDAV. The important detail is that it matches existing cards by vCard UID, not by name or email. Updates land in place instead of creating a second “Nick” every day.

A small state file records which cards the script created. If a contact disappears from Google, it removes only the copy it made; it will not touch contacts that exist only in Nextcloud. The script supports a dry run, runs daily from a systemd user timer, and keeps OAuth credentials in a 0600 file outside the repository.

./sync_contacts.py sync --dry-run   # inspect the changes
./sync_contacts.py sync             # write them

2. Making an old MP3 player happy

The player only understands FAT32, chokes on long or Unicode filenames, and sorts by filename. The pipeline reads a read-only rclone mount of the music library, transcodes FLAC to 320 kbps MP3, transliterates names to ASCII, strips FAT32-illegal characters, and writes both ID3v2.3 and ID3v1 tags for the old firmware.

Every output file is duration-checked against its source after writing. Re-running the sync skips existing files, so it doubles as an incremental update. A corrupt source track is logged and skipped instead of stalling the whole run. The card-format helper also refuses to proceed until you type WIPE, which is the only thing standing between a bad path and a very bad afternoon.

3. Backups that get checked

The schedule is the easy part. The useful part is proving the repository is readable and complete. A weekly timer runs restic’s read-verification against a random 5% subset, both locally and on the off-site copy. That catches corruption and missing data without reading the entire repository every week.

What it does not prove is that a full restore works end to end. That is why an automated restore drill is on the improvement list — a backup I have not restored from is still just a hopeful copy.

Security posture

  • Tailscale-only access. No public ports for admin or application interfaces.
  • Full-disk encryption with LUKS on the system drive.
  • App passwords instead of account passwords for sync clients.
  • Secrets in 0600 files outside the repo; config directories at 0700.
  • One-way syncs where possible — nothing writes back to Google.
  • Nightly automatic OS, firmware, and container updates.

What I’d do differently

  • Add monitoring and alerting earlier. For a while, the monitoring system was me noticing that something felt wrong.
  • Put the server on a UPS before the first power flicker, not after.
  • Move configuration into version-controlled infrastructure as code sooner.
  • Automate the restore drill, not just the backup.

What I learned

Keeping a server alive for a year teaches different lessons than building one. Most of the work is maintenance, documentation, and choosing the boring option. The interesting part is designing something that does not need me in the room.

That is the part I want to do professionally.
